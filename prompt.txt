## **2. Recommended architectural model**

Use a **feature-first modular monolith with vertical slices**, supported by a small shared infrastructure layer.

The architectural principles should be:

- Organize code by business capability, not exclusively by technical layer.
- Keep each feature mostly flat.
- Keep business logic inside its owning module.
- Share infrastructure, not unrelated business logic.
- Allow optional modules to be disabled or removed through a controlled provisioning mechanism.
- Introduce a new folder, interface or abstraction only when it solves an identifiable problem.

# **Cross-cutting architectural improvements**

## **13. Establish strict dependency boundaries**

The architecture should enforce the following dependency rules rather than merely document them.

| Source            | Allowed dependencies                                          |
| ----------------- | ------------------------------------------------------------- |
| Backend `core`    | External libraries and infrastructure                         |
| Backend modules   | Own implementation, core and explicit public module contracts |
| Backend workers   | Core and module job handlers                                  |
| Backend `main.py` | Application composition and registration                      |
| Frontend `app`    | Features, UI and lib                                          |
| Frontend features | Own implementation, UI, lib and explicit feature interfaces   |
| Frontend `ui`     | Generic utilities and UI dependencies                         |
| Frontend `lib`    | External libraries and generated contracts                    |

Avoid:

- Circular feature dependencies.
- Direct access to another module's private repositories.
- Business logic inside HTTP routers.
- Database queries inside HTTP middleware.
- Feature-specific business logic inside `core` or `lib`.
- Imports from frontend features into generic UI primitives.
- Duplicate wrappers that simply forward arguments.
- Hidden initialization and other side effects in package imports.

You already have appropriate tools for enforcing these boundaries in the repository:

| Existing file                              | Recommended enforcement                               |
| ------------------------------------------ | ----------------------------------------------------- |
| `backend/scripts/check_architecture.py`    | Python module dependency rules                        |
| `frontend/.dependency-cruiser.cjs`         | TypeScript dependency boundaries and circular imports |
| `frontend/knip.json`                       | Unused files, exports and dependencies                |
| `frontend/scripts/check-api-contract.mjs`  | API contract consistency                              |
| `frontend/scripts/check-design-system.mjs` | UI design consistency                                 |
| `frontend/scripts/check-bundle-size.mjs`   | Bundle-size regression limits                         |

Extend these existing tools rather than introducing several additional architecture-checking frameworks.

## **16. Additional performance improvements enabled by this architecture**

| Improvement                                | Expected benefit                                         |
| ------------------------------------------ | -------------------------------------------------------- |
| Lazy-load optional frontend feature routes | Smaller initial JavaScript bundle                        |
| Lazy-initialize AI providers and parsers   | Lower startup overhead where initialization is expensive |
| Disable unused capability initialization   | Lower resource consumption                               |
| Centralize LLM client lifecycle            | Connection reuse and consistent timeouts                 |
| Centralize database session handling       | Better transaction and connection management             |
| Standardize TanStack Query keys            | Fewer redundant network requests                         |
| Eliminate duplicate RAG execution paths    | Potentially lower retrieval latency and AI costs         |
| Shared asynchronous job dispatch           | Consistent retry and idempotency behavior                |
| Consolidate context construction           | Potentially lower token consumption                      |
| Keep heavy ingestion outside API workers   | Better API responsiveness under ingestion load           |
