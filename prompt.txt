# Fullstack Blueprint 2.0 — Frontend Modernization

## 1. Role and objective

Act as a principal frontend architect, senior full-stack developer, UI/UX engineer, AI application engineer, security engineer, and software quality engineer.

You are responsible for analyzing, modernizing, refactoring, and extending the frontend of this repository:

The repository is intended to serve as a reusable, production-ready application blueprint for developing different types of products, including:

- SaaS applications
- AI-powered applications
- Enterprise dashboards
- Document analysis and RAG applications
- Agent-based applications
- Workflow automation platforms
- Internal business applications
- Customer portals
- Data analytics platforms

The objective is not merely to redesign the existing application. The objective is to create a modern, modular, maintainable, accessible, scalable, customizable, AI-native frontend architecture that can accelerate the development of future applications.

Implement the modernization in clearly defined phases.

Do not simply provide recommendations or implementation plans. Inspect the repository, modify the actual code, install compatible dependencies, implement the required features, run tests, resolve failures, and update the documentation.

---

## 2. Fundamental engineering principles

Follow these principles throughout the implementation:

- Prefer simplicity, maintainability, and composability.
- Avoid unnecessary abstractions and premature optimization.
- Preserve existing functionality and business logic.
- Maintain backward compatibility with the existing FastAPI backend wherever possible.
- Keep the modular, feature-based frontend architecture.
- Follow SOLID, DRY, KISS, and separation-of-concerns principles pragmatically.
- Prefer composition over inheritance.
- Prefer strongly typed interfaces and discriminated unions.
- Avoid `any`, unsafe type assertions, duplicated interfaces, and unnecessary state.
- Use production-quality implementations rather than temporary placeholders.
- Do not introduce multiple libraries that solve the same problem.
- Prefer official, maintained, stable dependencies.
- Do not install experimental or prerelease dependencies into the default application.
- Keep optional capabilities genuinely optional.
- Do not expose secrets, credentials, access tokens, or private configuration.
- Preserve existing user changes.
- Never execute destructive database, storage, or infrastructure operations.
- Do not push changes or create remote pull requests unless explicitly authorized.

Before selecting or upgrading a library, verify its current stable version, official documentation, compatibility requirements, migration guides, security status, and maintenance activity.

Do not assume that a library version mentioned in this prompt is the latest available version.

- Exporting OpenAPI

## Phase 8 — Modernize routing and state management

### Routing

Evaluate React Router against TanStack Router.

Compare:

- Type-safe route parameters
- Type-safe navigation
- Search parameter validation
- Lazy loading
- Authentication guards
- Feature-module registration
- Error boundaries
- Data-loading integration
- Testing complexity
- Migration cost

Preserve React Router initially.

Only migrate to TanStack Router if the audit demonstrates a meaningful architectural benefit and a safe migration strategy.

Do not maintain two competing routers in the production application.

Preserve existing URLs, deep links, redirect behavior, and browser history.

### State management

Establish clear state ownership:

| State category | Solution |
|---|---|
| Server state | TanStack Query |
| Form state | React Hook Form |
| URL state | Router search parameters |
| Local UI state | React state |
| Theme and preferences | Context or dedicated preference store |
| Complex workspace state | Zustand where justified |
| Persistent offline data | IndexedDB/Dexie where justified |

Improve TanStack Query configuration:

- Centralized query keys
- Appropriate stale times
- Cache invalidation
- Query cancellation
- Mutation handling
- Optimistic updates where safe
- Pagination
- Infinite queries
- Error boundaries
- Session-related cache cleanup

Do not duplicate TanStack Query server data in Zustand.

### Acceptance criteria

- State ownership is documented.
- Route behavior remains backward compatible.
- Query and mutation behavior is predictable.
- Unnecessary global state is eliminated.
- Cross-user and cross-session cache leakage is prevented.

# Execution and phase-management protocol

Execute all phases sequentially.

Do not attempt a complete frontend rewrite in a single operation.

For every phase, follow this workflow:

### Step 1 — Inspect

Read relevant files, dependencies, documentation, previous implementation decisions, and tests.

### Step 2 — Plan

Identify the required changes, affected files, technical risks, compatibility concerns, and acceptance criteria.

### Step 3 — Implement

Modify the actual repository using production-quality code.

### Step 4 — Validate

Run relevant:

- Lint checks
- Type checks
- Unit tests
- Component tests
- Integration tests
- Browser tests
- Production builds

### Step 5 — Resolve

Investigate and fix failures introduced during implementation.

Do not proceed to dependent phases while significant regressions remain unresolved.

Independent phases may continue if a documented external blocker does not affect them.

### Step 6 — Document

Update:

```text
docs/frontend/MIGRATION_STATUS.md
docs/frontend/IMPLEMENTATION_LOG.md
docs/frontend/MODERNIZATION_PLAN.md
```

### Step 7 — Continue

Proceed automatically to the next phase when acceptance criteria are satisfied.

Do not request confirmation for routine implementation decisions.

Request user input only for genuine blockers, unavailable credentials, irreversible operations, or significant architectural decisions that cannot be resolved safely from repository context.

# Definition of done

The modernization is successful when:

- Existing functionality is preserved.
- The application builds and runs successfully.
- Core user journeys are tested.
- Material UI and Emotion are removed or any remaining exception is explicitly justified.
- The design system is centralized and configurable.
- Frontend architecture is modular and maintainable.
- API contracts are generated and synchronized.
- AI capabilities can be integrated without redesigning the frontend.
- Optional modules do not impose unnecessary dependencies.
- New products can reuse common UI components, layouts, integrations, and development workflows.
- The repository is significantly easier for both human developers and AI coding agents to extend.

The objective is to create a frontend foundation that can support an entire portfolio of applications rather than merely modernize one application.
